## 决策树

```text
┌──────────────────────────────────┐
│ 1 Resolve workflow               │
└────────────────┬─────────────────┘
                 │
                 ├──── 无在途流程 ────→ 3 Graph
                 ├──── 状态不明 ──────→ [多候选则澄清；证据不足则报告阻塞]
                 │
                 ▼ 唯一在途流程
┌──────────────────────────────────┐
│ 2 Resume                         │
└────────────────┬─────────────────┘
                 │
                 ├──── 可以推进 ────→ [执行并交接]
                 └──── 条件不足 ────→ [说明用户下一步操作]
┌──────────────────────────────────┐
│ 3 Graph                          │
└────────────────┬─────────────────┘
                 │
                 ├──── 失败/缺失 ────→ [停止并报告]
                 │
                 ▼ 通过
┌──────────────────────────────────┐
│ 4 Report                         │
└────────────────┬─────────────────┘
                 │
                 ├──── 通过 ─────────→ [结束]
                 └──── 失败/缺失 ────→ [停止并报告]
```

步骤 2 结束后不进入 3；步骤 3 仅由步骤 1「无在途流程」到达。

## 术语与数据结构

### 在途流程识别

在途范围包括全部 MDF workflow：既包括交付主线，也包括 init、bootstrap、intake、
prp review、CodeWiki、clarify 等尚未完成的流程及其内部委托。
结合当前对话的显式调用、已确认范围、待回答问题、失败与交接记录，以及目标现场识别。
已经完成、取消或被用户替代的流程不算在途；draft PRP、open Bug 或待办事项本身不代表流程已启动。

先核对本次目标；Git 仓库解析绝对 `REPO_ROOT` 并识别已有改动。
续办尚未 Git 化的 init/bootstrap 时按 `references/initialization.md` 核对普通目录和父仓库边界；
clarify 可仅依赖已确认议题，不要求 Git 仓库。不得在识别前统一要求 manifest ready 或 clean。

按需核对 manifest、当前分支、相关 worktree、产物、验证与恢复记录。
feature 使用 `references/delivery-contract.md`，通过 `delivery status` 查看身份、
阶段记录和 worktree 路径；按下一 intent 切到对应已有 worktree，缺树则停止。
按原阶段要求检查 gate 是否有效；不能仅凭文件存在或历史 passed 判断阶段完成。
不能仅凭 `next` CLI 的 in_progress 或当前 checkout 缺少材料断言没有在途流程。
非 feature 分支按原有交付语义判断，不套用 feature gate。

同一流程的内部委托先续办未完成的子步骤，再返回调用方。
多个独立候选且上下文未指定当前目标时，列出候选并询问用户选择；证据冲突或不足时说明缺项，
不猜测流程、初始化类型或阶段，也不把无法判定当作无在途而退回蓝图。
没有统一的 workflow 状态文件；使用已有上下文与产物，不新增状态协议。

### 续办与交接

完整读取所选 intent 及其要求的公共引用，以其编号工作流、前置条件和失败恢复规则为准。
先复核已完成步骤的证据，从尚未完成的步骤续办，不重做已验收且仍有效的操作。
交付主线的当前 intent 已完成而交付未结束时，可委托下一个阶段：
start → design → [write-tests ∥ implement] → converge → review → finish。
测试与实现都未完成时，沿用已有分工；无分工则先 write-tests，再由后续 next 推进 implement。
存在仍在运行的执行者时报告其进度或待交接项，不重复执行其工作。
缺失或过期证据按原阶段规则原地补验，不跳过门禁。

显式 next 授权在已确认范围内续办所选 intent，或进入交付主线的下一个 intent。
原流程的用户确认、输入、权限与验证要求继续适用，已有有效确认无需重复取得。
next 不代替方案确认、初始化启用确认或原流程要求的 Git 操作授权。
用户仅要求查看时保持只读，报告下一步。条件不足时明确说明：
当前流程与步骤、判定证据、阻塞原因，以及用户需要回答的问题、补充的材料或执行的命令。

一次 next 只续办一个所选 intent（包含其内部委托），完成后报告实际结果和后续步骤；
不自动串联其余主线，不在续办结束后追加蓝图。失败保留现场，按原流程交接。
无在途时不自动启动 init、start、prp review 或其他工作。

### PRP 蓝图

仅确认没有在途流程时进入本分支。只读，不要求 clean worktree，不创建或拆分 PRP。
运行 `python3 "$MDF_ROOT/scripts/mdf.py" next --repo "$REPO_ROOT" --depth <N>`；默认 3，N 为正整数。
本分支要求 ready；参数非法或仓库未就绪时报告原因和所需操作，不自动初始化。
depth 仅控制蓝图展示深度，不控制续办步数。
主报告仅 ready；根为全部依赖已满足的 ready。implemented/released 依赖视为满足；
milestone 依赖在该阶段不存在 draft 或 ready PRP 时满足。
多上游取最大依赖层级加一；重复节点用交叉引用并保留全部 blocked_by。同层按 PRP ID 排序。
显示进行中的 ready、未进入树的阻塞 ready、draft 的 prp review 提示和隐藏节点。
树的下游不表示完成一个上游即可开工。空结果明确说明；非法依赖停止，不输出误导性树。
蓝图不选择 MVP、不发现新需求、不创建或拆分 Proposal，不新增 mvp 入口。
